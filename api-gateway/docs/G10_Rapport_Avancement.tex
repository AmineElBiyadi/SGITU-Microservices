\section*{Objectifs}
\addcontentsline{toc}{section}{Objectifs}
Ce rapport presente l'avancement technique du microservice G10. Il decrit la conception, l'implementation, la securite, la documentation API, les tests et le deploiement Docker. Il montre aussi comment la Gateway coordonne les appels entre les clients et les microservices SGITU. \section{Presentation du microservice}

\subsection{Description du sous-systeme G10}

Le groupe 10 realise le sous-systeme \textbf{API Gateway \& Securite}. G10 constitue le point d'entree unique pour les clients Web, mobile ou Postman. Son role fonctionnel est de recevoir les requetes externes, d'appliquer les controles de securite transverses, puis de router chaque requete vers le microservice responsable.

Techniquement, le microservice est developpe avec Spring Boot, Spring Cloud Gateway, Spring Security WebFlux, JJWT, Swagger/OpenAPI et Docker. Il permet de centraliser la securite sans dupliquer la logique metier des autres groupes.

\subsection{Fonctionnalites metier implementees}

\begin{itemize}
  \item exposition d'un point d'entree commun pour les microservices SGITU ;
  \item routage vers les services G1 a G9 selon les prefixes REST ;
  \item validation des JWT recus dans le header \texttt{Authorization} ;
  \item controle d'acces selon les roles presents dans le JWT ;
  \item propagation des informations utilisateur vers les services cibles ;
  \item generation automatique d'un \texttt{X-Correlation-Id} lorsqu'il est absent ;
  \item gestion uniforme des erreurs techniques et de securite ;
  \item documentation des routes via Swagger/OpenAPI ;
  \item execution conteneurisee avec Docker et Docker Compose.
\end{itemize}

\subsection{Responsabilites de G10}

\begin{itemize}
  \item point d'entree unique du systeme SGITU ;
  \item validation stateless des JWT ;
  \item controle d'acces par role ;
  \item routage vers G1, G2, G3, G4, G5, G6, G7, G8 et G9 ;
  \item propagation de \texttt{X-User-Id}, \texttt{X-User-Email}, \texttt{X-Roles} et \texttt{X-Correlation-Id} ;
  \item gestion structuree des erreurs \texttt{400}, \texttt{401}, \texttt{403}, \texttt{404}, \texttt{503} et \texttt{504} ;
  \item journalisation avec SLF4J/Logback ;
  \item documentation Swagger/OpenAPI ;
  \item conteneurisation Docker.
\end{itemize}

\subsection{Ce que G10 ne fait PAS}

\begin{calloutsuccess}
G3 est la source de verite pour les utilisateurs, les profils, les roles, les permissions, les mots de passe et l'emission des JWT. G10 ne possede donc pas de base utilisateurs et ne genere pas les tokens d'authentification.
\end{calloutsuccess}

G10 ne modifie pas directement les comptes, les roles ou les permissions. Toute operation d'identite est routee vers le service utilisateur. La Gateway reste un composant transversal : elle controle, enrichit et route les requetes, mais ne devient pas proprietaire des donnees metier.

\subsection{Logs et tracabilite}

Les captures des logs permettent de verifier que la requete entre par G10, que le JWT est valide, que les headers de contexte sont ajoutes, puis que la requete arrive au microservice cible. Le \texttt{X-Correlation-Id} sert a relier les logs entre les services.

Pour observer les logs des trois services, nous utilisons un scenario de tracabilite compose de deux requetes Postman successives. \section{Securite}

\subsection{Contrat JWT}

G10 attend un JWT emis par le service d'authentification. Le token est envoye par le client dans :

\begin{lstlisting}[style=codeStyle]
Authorization: Bearer <JWT_EMIS_PAR_G3>
\end{lstlisting}

Claims minimaux :

\begin{lstlisting}[style=codeStyle]
{
  "sub": "user@sgitu.ma",
  "roles": ["ROLE_USER"],
  "userId": 10,
  "iat": 1715000000,
  "exp": 1715003600,
  "jti": "uuid"
}
\end{lstlisting}

\begin{center}
\begin{tabular}{>{\bfseries}p{3cm} p{8.5cm}}
\rowcolor{navyblue}
\color{white}\textbf{Claim} & \color{white}\textbf{Role} \\
\hline
\texttt{sub} & Email ou identifiant principal de l'utilisateur. \\
\rowcolor{lightgray}
\texttt{roles} & Liste des roles autorisant les routes protegees. \\
\texttt{userId} & Identifiant fonctionnel de l'utilisateur. \\
\rowcolor{lightgray}
\texttt{iat} & Date de creation du token. \\
\texttt{exp} & Date d'expiration du token. \\
\rowcolor{lightgray}
\texttt{jti} & Identifiant optionnel du token pour la tracabilite. \\
\end{tabular}
\end{center}

G10 verifie la signature, l'expiration, le \texttt{sub} et au moins un role dans \texttt{roles} ou \texttt{role}. Il ne stocke pas localement les utilisateurs, les mots de passe ou les tokens.

\begin{calloutdanger}
G10 ne doit pas maintenir de copie locale des comptes, roles ou permissions. Toute modification d'identite doit rester conforme a la separation definie en section 1.4.
\end{calloutdanger}

\subsection{Spring Security WebFlux}

La configuration \texttt{SecurityConfig} desactive CSRF pour l'API REST, declare les routes publiques, applique les regles RBAC, puis ajoute le filtre \texttt{JwtAuthFilter}. Lorsqu'un token est valide, le filtre construit une authentification Spring Security avec les roles extraits du JWT.

\begin{itemize}
  \item \texttt{/auth/login}, Swagger et Actuator sont publics ;
  \item \texttt{POST /api/users} est public pour permettre l'inscription ;
  \item les routes d'administration utilisateurs exigent \texttt{ROLE\_ADMIN} ;
  \item les analytics et le ML de G8 exigent \texttt{ROLE\_ADMIN}, \texttt{ROLE\_OPERATOR} ou \texttt{ROLE\_STAFF} ;
  \item les autres routes \texttt{/api/**} exigent un JWT valide.
\end{itemize}

\begin{center}
\begin{tabular}{>{\bfseries}p{3cm} p{8.8cm}}

\hline

\subsection{Gestion des erreurs de securite}

\textbf{401 Unauthorized} : le client n'est pas authentifie ou le JWT est invalide.

\begin{lstlisting}[style=codeStyle]
{
  "status": 401,
  "error": "Unauthorized",
  "code": "INVALID_TOKEN",
  "message": "JWT invalide ou expire"
}
\end{lstlisting}

\textbf{403 Forbidden} : le JWT est valide, mais le role ne permet pas d'acceder a la route.

\begin{lstlisting}[style=codeStyle]
{
  "status": 403,
  "error": "Forbidden",
  "code": "FORBIDDEN",
  "message": "Acces refuse pour ce role"
}
\end{lstlisting}

\subsection{Fonctionnalites en cours}

\begin{itemize}
  \item validation progressive des routes definitives avec les autres groupes ;

\subsection{Difficultes rencontrees}

\begin{itemize}
  \item clarification de la responsabilite JWT entre le service utilisateur et la Gateway ;
  \item alignement des roles utilises pour G8 : choix de \texttt{ROLE\_OPERATOR} et \texttt{ROLE\_STAFF} ;
  \item configuration du reseau Docker commun \texttt{sgitu-network} pour permettre la communication inter-services ;
  \item verification du routage entre services developpes par des groupes differents.
\end{itemize}

\subsection{A verifier avec les autres groupes}

\begin{itemize}
  \item stabilite du format JWT utilise par les services ;
  \item maintien du secret ou de la cle publique de verification JWT ;
  \item endpoints definitifs des autres groupes ;
  \item disponibilite des microservices cibles dans le meme reseau Docker.
\end{itemize}

\section{Conclusion}

Le microservice G10 fournit une API Gateway securisee, documentee, testable et conteneurisee pour le projet SGITU. Il centralise les controles transverses, applique la securite JWT, propage les headers utiles et route les requetes vers les microservices metiers. L'etat actuel permet une demonstration avec Swagger, Postman, Docker Compose et les logs de tracabilite.
