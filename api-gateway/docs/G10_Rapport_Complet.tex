\section{Introduction et perimetre du microservice}

\subsection{Contexte de la livraison finale}

Le projet SGITU a pour objectif de construire un systeme distribue pour la gestion intelligente des transports urbains. Chaque groupe realise un microservice autonome correspondant a un sous-systeme du domaine : billetterie, abonnements, utilisateurs, coordination, notifications, paiement, suivi des vehicules, analytique et incidents.

Le groupe 10 occupe une position transversale : il fournit l'API Gateway et la couche de securite d'entree. Il ne remplace pas les microservices metier. Son role est de recevoir les requetes externes, appliquer les controles communs, puis transmettre les appels vers le service responsable.

\begin{successBox}
Le perimetre G10 est conforme a la consigne finale : API REST fonctionnelle, documentation Swagger, securite JWT, Dockerfile, docker-compose, README, tests Postman, monitoring Prometheus/Grafana et simulation Kubernetes.
\end{successBox}

\subsection{Valeur ajoutee du groupe 10}

Sans API Gateway, chaque client devrait connaitre les ports, les adresses, les regles d'authentification et les chemins internes de tous les microservices. Cela creerait un couplage fort avec les services metier. G10 simplifie cette architecture en exposant un point d'entree unique :

\begin{lstlisting}[style=code]
Client / Postman / Frontend -> http://localhost:8080 -> G10 -> G1..G9
\end{lstlisting}

La Gateway permet donc :

\begin{itemize}
  \item une entree unique pour les clients externes ;
  \item une validation centralisee du JWT ;
  \item un controle d'acces avant le routage ;
  \item une propagation uniforme des headers utilisateur ;
  \item une reponse propre si un microservice cible est indisponible ;
  \item une observabilite centralisee via logs, Actuator, Prometheus et Grafana.
\end{itemize}

\subsection{Responsabilites de G10}

\begin{longtable}{p{4.5cm}p{10cm}}
\toprule
\textbf{Responsabilite} & \textbf{Description} \\
\midrule
Routage & Rediriger les appels REST vers G1 a G9 selon les prefixes. \\
Securite & Valider le token JWT, verifier l'expiration et extraire les roles. \\
RBAC & Autoriser ou refuser l'acces selon les roles. \\
Headers & Injecter \texttt{X-User-Id}, \texttt{X-User-Email}, \texttt{X-Roles}, \texttt{X-User-Role}, \texttt{X-Source-Group}. \\
Correlation & Generer ou propager \texttt{X-Correlation-Id}. \\
Erreurs & Retourner des erreurs JSON coherentes pour \texttt{401}, \texttt{403}, \texttt{404}, \texttt{503}. \\
Blacklist & Prendre en charge la revocation des tokens via Redis lorsque l'option est active. \\
Observabilite & Exposer \texttt{/actuator/prometheus} et alimenter Grafana. \\
\bottomrule
\end{longtable}

\subsection{Ce que G10 ne fait pas}

\begin{warningBox}
G10 ne gere pas les comptes, les mots de passe, les profils, les roles ni l'emission des JWT. Ces responsabilites appartiennent au service utilisateur G3, qui reste la source de verite. G10 valide seulement les tokens recus et utilise leurs claims pour proteger les routes.
\end{warningBox}

\section{Conception avancee}

\subsection{Architecture globale SGITU}

\diagram{diagrams/g10_01_architecture_globale.png}{0.95}{Architecture globale avec G10 comme point d'entree}

L'architecture finale conserve une separation claire entre les services. Les clients n'appellent pas directement les ports metier exposes dans le reseau Docker. Dans la demonstration, les appels passent par la Gateway, qui applique d'abord la securite puis route vers le service cible.

\subsection{Diagramme de composants}

\diagram{diagrams/g10_02_diagramme_composants.png}{0.95}{Diagramme de composants de l'API Gateway}

Les composants principaux sont les suivants :

\begin{longtable}{p{4cm}p{10cm}}
\toprule
\textbf{Composant} & \textbf{Role} \\
\midrule
\texttt{SecurityConfig} & Definit les routes publiques, les routes protegees et les roles autorises. \\
\texttt{JwtAuthFilter} & Lit le header \texttt{Authorization}, valide le token et cree l'authentification WebFlux. \\
\texttt{JwtService} & Parse le JWT, verifie la signature, l'expiration, le subject, \texttt{userId}, \texttt{role}/\texttt{roles} et \texttt{jti}. \\
\texttt{TokenBlacklistService} & Verifie si un token a ete revoque apres logout. \\
\texttt{GatewayHeadersFilter} & Injecte les headers utilisateur et journalise request/response avec correlation id. \\
\texttt{ApiErrorWriter} & Produit les reponses JSON d'erreur. \\
\texttt{GatewayExceptionHandler} & Transforme les erreurs techniques en \texttt{503} ou \texttt{500} lisibles. \\
\bottomrule
\end{longtable}

\diagram{diagrams/g10_03_diagramme_cas_utilisation.png}{0.82}{Cas d'utilisation principaux}

Les acteurs principaux sont le client externe, l'administrateur, l'operateur, le passager et les microservices cibles. Les cas d'utilisation couvrent le login route vers G3, l'appel d'une route protegee, l'acces analytics, l'envoi de notification, l'appel paiement et la consultation des etats de supervision.

\diagram{diagrams/g10_09_diagramme_classes_gateway.png}{0.95}{Diagramme de classes simplifie}

Le diagramme de classes ne contient pas d'entite \texttt{User}, \texttt{Role} ou \texttt{Permission}, car ces elements appartiennent au domaine de G3. Les classes G10 sont techniques : filtres, services de validation, objets de principal JWT et gestionnaires d'erreurs.

\subsection{Source de verite des donnees}

\diagram{diagrams/g10_04_modele_base_donnees.png}{0.86}{Responsabilite des donnees utilisateurs}

G10 est stateless pour les donnees metier. La seule persistance technique ajoutee dans la livraison finale est Redis pour la blacklist des tokens revoques. Redis ne contient pas les utilisateurs ; il contient uniquement des identifiants de tokens ou des empreintes avec une duree de vie limitee.

\section{Securite}

\subsection{Contrat JWT}

Le token JWT est transmis dans le header suivant :

\begin{lstlisting}[style=code]
Authorization: Bearer <access_token>
\end{lstlisting}

Claims attendus :

\begin{longtable}{p{3cm}p{4cm}p{7cm}}
\toprule
\textbf{Claim} & \textbf{Exemple} & \textbf{Role} \\
\midrule
\texttt{sub} & \texttt{admin.g10@sgitu.ma} & Identifiant principal, generalement email. \\
\texttt{userId} & \texttt{1} & Identifiant utilisateur propage aux services. \\
\texttt{roles} & \texttt{["ROLE\_ADMIN"]} & Liste des roles. \\
\texttt{role} & \texttt{ROLE\_USER} & Ancien format accepte pour compatibilite. \\
\texttt{iat} & \texttt{1778204092} & Date d'emission. \\
\texttt{exp} & \texttt{1778290492} & Date d'expiration. \\
\texttt{jti} & \texttt{uuid} & Identifiant du token, utile pour blacklist. \\
\bottomrule
\end{longtable}

\subsection{Secret partage et perspective RS256}

Dans la version actuelle, G3 et G10 utilisent un secret HS256 partage via variable d'environnement \texttt{JWT\_SECRET}. Ce choix est simple pour la demonstration locale et permet a G10 de verifier les tokens emis par G3.

\begin{warningBox}
Pour une version production, la solution recommandee est RS256 : G3 signe avec une cle privee, et G10 verifie avec une cle publique. Cela evite de partager le secret de signature entre plusieurs services.
\end{warningBox}

\subsection{Spring Security WebFlux}

La configuration WebFlux desactive CSRF, declare les routes publiques et applique les roles sur les routes sensibles. Le filtre JWT est ajoute dans l'ordre \texttt{AUTHENTICATION}.

\begin{lstlisting}[style=code]
.pathMatchers("/auth/login", "/auth/refresh",
              "/actuator/**", "/swagger-ui/**",
              "/v3/api-docs/**").permitAll()
.pathMatchers(HttpMethod.POST, "/api/users").permitAll()
.pathMatchers("/api/v1/analytics/**", "/predict/**")
    .hasAnyAuthority("ROLE_ADMIN", "ROLE_OPERATOR", "ROLE_STAFF")
.pathMatchers("/api/**").authenticated()
.addFilterAt(jwtAuthFilter, SecurityWebFiltersOrder.AUTHENTICATION)
\end{lstlisting}

\end{lstlisting}

\subsection{Blacklist token et logout}

La livraison finale ajoute Redis pour prendre en charge la revocation des tokens. Lorsqu'un logout est traite, le token ou son \texttt{jti} peut etre marque comme revoque jusqu'a son expiration naturelle. G10 verifie ensuite la blacklist avant d'accepter un token.

\begin{lstlisting}[style=code]
TOKEN_BLACKLIST_ENABLED=true
REDIS_HOST=redis
REDIS_PORT=6379
\end{lstlisting}

\begin{infoBox}
Cette blacklist repond a la remarque du rendu intermediaire : un token JWT stateless reste valide jusqu'a son expiration ; Redis ajoute une couche de revocation pour le logout.
\end{infoBox}

\subsection{Securite reseau}

Pour la demonstration, le client externe utilise \texttt{localhost:8080}. Dans une configuration plus stricte, les ports metier G1 a G9 ne doivent pas etre publies vers l'hote ; ils doivent rester accessibles seulement dans \texttt{sgitu-network}. Cette approche reduit le risque de contournement de la Gateway.

\begin{infoBox}
Dans Docker, un conteneur appelle un autre conteneur avec son nom de service, par exemple \texttt{http://api-gateway:8080}. Depuis Postman ou le navigateur sur la machine, on utilise \texttt{http://localhost:8080}.
\end{infoBox}

\section{Resilience et challenge chaos}
